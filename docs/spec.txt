
# Vasal specification
#
# The single source of truth for what the game and its programs do: every
# feature, mechanism, rule and corner case, written as stories. Code and
# tests point at stories and their acceptance criteria by id, and tools
# check the two against each other.
#
# ---- Format ----
#
# A story starts with "story <id>" at column 0 and has fields indented by
# one tab. A field's text continues on lines indented one tab deeper. Lines
# starting with # are comments; empty lines separate stories. ASCII only,
# tabs, LF, at most 80 columns (tab width 4).
#
#	story <id>
#		title: <one line>
#		milestone: <0 to 7, or later>
#		links: <story ids, separated by spaces>
#		description: <free text: what and why>
#		value <name>: <number or open> <unit> [<min>..<max>] [fixed]
#		criterion <n>: <test> [proposed | open]
#			given: <the situation>
#			when: <what happens>
#			then: <the expected result, in words>
#			expect: <quantity> <operator> <value>
#			why: <the reason, when it is not obvious>
#
# Ids are lowercase words joined by dots (combat.duel). An id never changes
# meaning and is never reused. A criterion is referred to as <story id>#<n>
# (combat.duel#3); its number never changes, new criteria get the next
# number.
#
# links, value and criterion are optional and may repeat (links once).
# given and when are optional; then is required; expect may repeat.
#
# value: a number the story depends on. Its key is <story id>.<name>
# (combat.strike.parry_chance). "open" means not decided yet; the range
# is the allowed span. Values are tuning data kept in data files, which are
# generated from this file; "fixed" values are hard limits, generated into
# a C header instead. Units: percent, ticks, distance, gold, troops, count.
#
# criterion: one acceptance criterion. <test> says how it is checked:
#	unit         a cairo unit test
#	scenario     a scripted match with a fixed seed
#	statistics   a scenario over many seeds, checking a range
#	fuzz         a fuzz target
#	lint         a lint check
#	review       read by a person; only when nothing else works
# Without a status the criterion is agreed by the user. proposed: written
# by Claude to close a gap in the design, waiting for the user's decision.
# open: not decided; the text says what is missing.
#
# expect: a result a tool can compare. <quantity> is a dotted name of
# something a test measures (duel.strikes.average), <operator> is one of
# = != < <= > >= in ~ (~ means equal within the statistical tolerance of
# the test), and <value> is a number, a range <min>..<max>, a word
# (true, false, none) or a value key in braces ({combat.strike.parry_chance}).
#
# ---- References from code and tests ----
#
# A comment holding "spec:" and ids: "// spec: combat.duel#3 combat.wound".
# A test names the criteria it checks; code names the stories it
# implements.
#
# ---- Checks (planned tool) ----
#
#	- the file parses; ids are unique and well formed
#	- every link and every "spec:" reference exists
#	- every agreed criterion, except review, has a test referring to it
#	- data files and the limits header are generated from the values, so
#	  code never repeats a number

story flow.start
	title: Opening the game
	milestone: 5
	links: client.platform server.web flow.main_menu
	description: The player opens the game's address in a browser. The
		page loads the client, which shows a loading screen until it is
		ready, then the main menu.
	criterion 1: review
		when: The player opens the game's address.
		then: A loading screen shows progress until the client is ready,
			then the main menu appears.
	criterion 2: unit proposed
		when: The client can't reach the server.
		then: The main menu says the server is unreachable and offers to
			try again.
	criterion 3: unit proposed
		given: A browser tab whose vasal is alive, within the grace period.
		when: The page is reloaded.
		then: The client reconnects to that vasal and goes straight to the
			game, skipping the main menu.

story flow.main_menu
	title: Main menu
	milestone: 5
	links: players.join players.cap match.win
	description: The main menu holds a name field and the list of
		alliances, each with its color, name, number of players and cap.
		The player picks an alliance with room and presses Join. The list
		updates live while the menu is open.
	criterion 1: unit
		then: Join is enabled only with a valid name and an alliance with
			room selected.
	criterion 2: unit
		then: Full alliances are shown as full and can't be selected.
	criterion 3: scenario proposed
		given: The main menu open.
		when: A place frees or fills in an alliance.
		then: The menu shows the new count within one second.
	criterion 4: unit proposed
		then: The client remembers the last name used in the browser and
			fills it in.
	criterion 5: review proposed
		given: A match that has ended and not yet restarted.
		then: The menu says a new match starts soon and Join is disabled.

story flow.join
	title: Joining
	milestone: 5
	links: players.join players.cap network.protocol
	description: Pressing Join sends the name and alliance to the server,
		which accepts or refuses the player.
	criterion 1: scenario
		when: The server accepts the join.
		then: The client shows the match with the camera on the new vasal's
			centaine.
	criterion 2: scenario
		when: The server refuses the join (alliance full, name taken,
			outdated client, match over).
		then: The client stays in the main menu and shows the reason; an
			outdated client asks the player to reload.

story flow.playing
	title: Playing
	milestone: 5
	links: client.render client.hud client.input
	description: The match view with the map, the HUD and the minimap, as
		described in the client stories.
	criterion 1: review
		then: The player can play using only what the match view shows.

story flow.leave
	title: Leaving on purpose
	milestone: 5
	links: match.disconnect
	description: The player can leave the match from a menu in the match
		view.
	criterion 1: scenario proposed
		when: The player confirms leaving.
		then: It counts as a disconnect: the centaine stays for the grace
			period and can still be attacked, and the player is brought to
			the main menu.
		why: Leaving must not be a way to save a centaine from a lost fight.
	criterion 2: review open
		then: Whether a player who left can start a new vasal in another
			alliance while their old centaine is still in its grace period.

story flow.death
	title: Dying
	milestone: 5
	links: players.vasal match.rejoin players.cap
	description: When the vasal dies, the player sees that their vasal has
		fallen, with their statistics, and is brought back to the main
		menu. Their alliance has one player fewer.
	criterion 1: scenario
		when: The vasal's last troop dies or deserts.
		then: The client shows the death message and the vasal's
			statistics, then the main menu.
	criterion 2: scenario
		when: The vasal dies.
		then: The alliance's player count drops by one in that tick.

story flow.match_over
	title: The match ends
	milestone: 5
	links: match.win match.stats
	description: When an alliance wins, every player sees the match-over
		banner with results and statistics, then returns to the main menu.
	criterion 1: scenario
		when: An alliance wins.
		then: Every connected client shows the banner with the results.
	criterion 2: scenario proposed
		when: The player closes the banner, or after a while.
		then: The client returns to the main menu, where joining waits for
			the next match.

story flow.connection_lost
	title: Losing the connection
	milestone: 5
	links: match.disconnect network.liveness
	description: When the connection drops during a match, the client tries
		to reconnect by itself.
	criterion 1: scenario proposed
		when: The connection drops.
		then: The client says it is reconnecting and retries for the whole
			grace period.
	criterion 2: scenario
		when: It reconnects within the grace period.
		then: The player continues with the same vasal.
	criterion 3: scenario
		when: The grace period ends first.
		then: The client shows that the vasal is gone, then the main menu.

story players.join
	title: Joining a match
	milestone: 5
	links: players.alliance match.capacity match.spawn
		flow.main_menu
	description: A player enters a name, picks one of the alliances that
		has room, and joins the running match as a new vasal with a small
		starting centaine and some gold. There is no matchmaking and no queue.
		There are no accounts in the first build.
	value name_length: 16 count fixed
	criterion 1: scenario
		given: A running match with room in alliance 2.
		when: A player joins alliance 2.
		then: A new vasal of alliance 2 appears with the starting centaine and
			the starting gold.
		expect: alliance.2.players = 1
	criterion 2: unit proposed
		then: A name is 1 to {players.join.name_length} characters long and
			holds only letters, digits, spaces, hyphens and underscores,
			without leading or trailing spaces. Any other name is refused
			with a message saying why.
	criterion 3: unit proposed
		given: A player named "Arn" in the match.
		when: Another player joins as "arn".
		then: The name is refused as taken; names are compared without
			regard to case.

story players.alliance
	title: Alliances
	milestone: 5
	links: combat.enemies capture.requirement economy.payout
	description: A match has a fixed number of alliances. Members can't
		attack each other, and their troops count as one side: they pool
		for captures and fight together. Each player still controls only
		their own troops, and troops never change owner. Settlements are
		captured for the alliance, never for one player.
	value count: open count 2..8
	criterion 1: unit
		when: A player orders a vintaine that belongs to another player of
			the same alliance.
		then: The order is refused and nothing changes.
	criterion 2: unit
		then: No action moves a troop from one player to another.
	criterion 3: scenario
		given: Two players of one alliance with troops at a settlement.
		when: The settlement is captured.
		then: It belongs to the alliance, not to either player.

story players.cap
	title: Room in an alliance
	milestone: 5
	links: players.alliance match.capacity flow.main_menu flow.death
	description: The server's only limit on joining is a cap per alliance:
		the match's player limit divided by the number of alliances,
		rounded down. A vasal who dies frees their place, so the same player
		or anyone else can take it.
	criterion 1: unit
		given: A player limit of 100 and 4 alliances.
		then: Each alliance holds at most 25 players.
		expect: alliance.cap = 25
	criterion 2: unit
		given: A player limit of 100 and 3 alliances.
		then: Each alliance holds at most 33 players; the match at most 99.
		expect: alliance.cap = 33
	criterion 3: scenario
		given: A full alliance.
		when: A player tries to join it.
		then: The join is refused as full; the player stays in the main
			menu and can pick another alliance.
	criterion 4: scenario
		given: A full alliance.
		when: One of its vasals dies.
		then: The alliance has room for one player at once.
	criterion 5: scenario
		given: An alliance with room for one more player.
		when: Two players join it in the same tick.
		then: The server takes the join it received first; the other is
			refused as full.
	criterion 6: unit proposed
		given: A disconnected player within the grace period.
		then: They still hold their place in the alliance.
		why: Otherwise a reconnecting player could find their own alliance
			full.

story players.side
	title: The side choice is locked
	milestone: 5
	links: players.vasal match.disconnect
	description: A player's choice of alliance holds until the
		vasal dies. Only a new vasal may choose again.
	criterion 1: unit
		then: A living vasal can't change alliance.
	criterion 2: scenario
		given: A vasal who disconnects and reconnects within the grace
			period.
		then: The vasal keeps the same side.
	criterion 3: scenario
		given: A dead vasal.
		when: The player rejoins.
		then: The player chooses a side again.

story players.vasal
	title: A vasal lives through their troops
	milestone: 5
	links: economy.desertion match.rejoin
	description: The player is the vasal, a commander who never appears on
		the map. The vasal is dead the moment their last troop dies or
		deserts.
	criterion 1: scenario
		when: The vasal's last troop is killed.
		then: The vasal is dead in that tick, and the player is brought back
			to the main menu.
	criterion 2: scenario
		when: The vasal's last troop deserts.
		then: The vasal is dead, the same as when the last troop is killed.
	criterion 3: unit proposed
		when: A vasal dies.
		then: Their gold is lost, and their capture contributions count as
			if they had left the match. A rejoining player is a new vasal
			and inherits nothing.
	criterion 4: unit proposed
		then: An empty vintaine has no position on the map and can't be given
			orders.

story map.space
	title: Map space
	milestone: 1
	links: map.terrain mapfile.format map.camera
	description: The map is a 2D grid of square tiles. Distances in this
		specification are measured in tiles. Positions use fixed-point
		numbers with a fraction of a tile as their smallest step, so the
		simulation never needs floating point. The map is huge: it must
		hold 100 centaines with room to manoeuvre, besides settlements and
		terrain, so the view is a tiny part of it, likely in the order of
		500 by 500 to 1000 by 1000 tiles. It must not be so large that
		players never meet; the spread of spawn areas and settlements
		decides how often they do.
	value width: open count
	value height: open count
	value max_side: 2048 count fixed
	value precision: 256 count fixed
	criterion 1: unit
		then: A position is stored in 1/{map.space.precision} of a tile, in
			numbers wide enough for a map of {map.space.max_side} tiles a
			side.
	criterion 2: unit
		then: No troop, NPC or treasure is ever outside the map.
	criterion 3: unit
		when: An order targets a position outside the map.
		then: The order is refused, and the player gets a notice saying
			why.
	criterion 4: unit proposed
		then: A map with a side longer than {map.space.max_side} tiles is
			refused.

story map.terrain
	title: Terrain
	milestone: 1
	links: vintaines.movement vintaines.pace editor.tools mapfile.format
	description: Every tile has a terrain type, and terrain decides where
		troops can go and how fast. Each map defines its own terrain types
		in the editor, with their values, and stores them in its file: for
		example forest and water that vintaines can't pass, tall grass
		that slows them a lot, short grass that slows them a little, and
		roads at full speed. Decorations (a lone tree, a rock) are only
		drawn and change nothing.
	criterion 1: unit
		then: No troop or NPC ever stands on an impassable tile.
	criterion 2: scenario
		when: A vintaine is ordered to an impassable tile or to an area it
			can't reach.
		then: It goes to the nearest point it can reach.
	criterion 3: unit
		given: A terrain type with a speed of 60 percent.
		then: A troop crossing it moves at 60 percent of its speed.
	criterion 4: scenario
		given: A short way through tall grass and a longer way along a road
			that takes less time.
		then: The vintaine takes the road: paths are the fastest, not the
			shortest.
	criterion 5: unit
		then: A map's terrain types, with their passability and speed, are
			stored in its file; there are no terrain values outside it.
	criterion 6: unit proposed
		given: A vintaine in step whose troops stand on different terrain.
		then: Each troop moves at the vintaine's pace times the speed of
			the tile it stands on, so the vintaine bunches up in slow
			ground and stretches out again after it.
	criterion 7: unit proposed
		given: Slow ground, with a road through it that runs a few regions
			away from the straight line between two points.
		then: A vintaine sent from one point to the other takes the road
			when it is faster: the coarse level of the search knows that a
			region crossed by a road is fast along the road.
	criterion 8: unit proposed
		given: A patch of tall grass on the straight line between two
			points, with short grass around it.
		then: Pulling the path straight never cuts through the tall grass
			when going around it is faster.

story map.camera
	title: Camera and view
	milestone: 1
	links: vintaines.focus map.sight troops.scout client.input
	description: The game fills the whole browser window. The camera always
		follows the player's focused vintaine and zooms by itself; the
		player controls neither, so a player sees only where their troops
		are. The camera frames the sight of the focused vintaine alone,
		with a margin of grayed terrain around it, to fit the monitor the
		browser is on, not the browser window; other selected vintaines
		change neither where it looks nor its zoom, and the player sees
		them by moving the focus with Tab. The window shows the middle of
		that picture: resizing the window crops or reveals around the
		middle and never rescales what is drawn. When that sight grows,
		because scouts join, the camera zooms out to keep all of it in the
		window; when it shrinks, the camera zooms back in. The zoom never
		frames more than a maximum that is the same for every player.
		Beyond the player's sight the window shows the terrain grayed and
		no units (map.sight), so a larger window only shows more gray
		terrain, which every player knows from the map anyway.
	value margin: open percent
	value glide: open ticks
	value max_frame: open distance
	criterion 1: unit
		then: The framed sight, an ellipse in the isometric view, fits
			the monitor with a margin of {map.camera.margin} percent of
			grayed terrain, so every player sees the same framing on any
			monitor of the same shape.
		why: A larger screen must not reveal more units or frame the sight
			differently.
	criterion 2: unit
		given: Several selected vintaines, near each other or not.
		then: The camera frames the focused vintaine's sight alone: it
			neither zooms out nor centers between them.
	criterion 3: unit
		when: The player adds a vintaine to the selection.
		then: The camera moves to it, since the last selected vintaine is
			focused (vintaines.focus).
	criterion 4: unit
		then: The camera never frames more than {map.camera.max_frame}
			tiles across, however far the sight reaches.
	criterion 5: unit
		then: The camera stays centered on the focused vintaine as it
			moves, even at the map's edges, where the window shows a plain
			dark ground beyond them (the map is a diamond on the screen, so
			its corners can't fill the window). The player can't move or
			zoom the camera.
	criterion 6: unit
		when: The focus changes to another vintaine.
		then: The camera glides to it over {map.camera.glide} ticks
			instead of jumping.
	criterion 7: review
		then: The zoom changes smoothly, without jumps, as troops move and
			the selection changes.
	criterion 8: unit
		when: The browser window is resized.
		then: The scale of what is drawn stays the same; the window shows
			more or less of the picture around its middle.
	criterion 9: unit
		when: The browser window moves to a monitor of another size.
		then: The picture is scaled for the new monitor.
	criterion 10: review
		then: The game is drawn sharp on high-density screens, and the
			interface (minimap, gold, alerts) stays at the window's edges
			and corners rather than being cropped with the map.

story map.minimap
	title: Minimap
	milestone: 1

	criterion 1: review
		then: The minimap shows the whole map with the player's alliance

	criterion 2: review proposed
		then: The player's own vintaines and centenar are always shown on

story map.regions
	title: Territory
	milestone: 4
	links: map.minimap
	description: Each settlement owns the region of tiles closer to it than
		to any other settlement. Territory of an alliance is the regions of
		its settlements. Regions are computed once when a map is loaded.
	criterion 1: unit proposed
		then: Every passable tile belongs to the region of its nearest
			settlement; equal distances go to the lower settlement id.

story map.sight
	title: Sight
	milestone: 1
	links: map.minimap map.camera troops.scout network.interest
		security.visibility
	description: A player sees only what their troops see. There is no
		scouting mechanic of its own: every troop sees a circle around it,
		whose radius depends on its type, and the player's sight is all
		those circles together. Inside it the player sees the terrain in
		full color and every troop and NPC, in the main view and on the
		minimap. Outside it the terrain is still drawn, grayed, and no
		troops or NPCs are shown. The edge fades softly from color to gray.
		Settlements are always shown, since the map is known.
	criterion 1: unit
		given: Two of the player's vintaines far apart.
		then: Each shows its own sight, and units in either are shown.
	criterion 2: unit
		then: Outside the player's sight the terrain is drawn grayed and no
			troops or NPCs are drawn.
	criterion 3: review
		then: The edge of sight fades softly from color to gray.
	criterion 4: review proposed
		then: Settlements are shown everywhere, inside sight or not.
	criterion 5: scenario open
		then: Whether allies share what their troops see.

story map.contents
	title: What a map holds
	milestone: 1
	links: mapfile.format editor.tools settlements.types npcs.bandits
	description: A map is the descriptor of everything on it, all set in
		the editor: its terrain types and the terrain of every tile,
		settlements of several types (villages, towns, castles, cities and
		others) with their areas, radii and flags, spawn areas for new
		vasals, bandit camps and decorations. Caravans travel between the
		settlements; treasure spawns on free tiles.
	criterion 1: unit
		then: A map without at least one settlement and one spawn area is
			refused.

story troops.types
	title: Troop types
	milestone: 2
	links: combat.ranged combat.sidearm
	description: Melee infantry: spearman, swordsman, battle axe
		infantry, heavy infantry, light infantry. Ranged: archer, thrower
		(axe, knife or spear), crossbowman, slinger. Ranged types differ in
		range and damage. Scouts see farther and move faster but fight
		poorly (troops.scout). No cavalry or siege units. The first build
		has the spearman, swordsman, archer, thrower and scout; the others
		come later. The centenar is a type of its own. Each type's speed,
		sight, skill, equipment, cost and salary are tuning data.
	criterion 1: unit proposed
		then: The first build offers exactly the spearman, swordsman,
			archer, thrower and scout.
	criterion 2: unit
		then: Each troop's sight radius is its type's (map.sight).

story troops.skill
	title: Skill
	milestone: 2
	links: combat.strike troops.tiers troops.recruit
	description: Each troop has a skill value that shifts its odds in
		combat. Skill comes from the troop type, its tier and the place it
		was recruited.
	criterion 1: unit
		then: A troop's skill is the sum of its type's base skill, its
			tier's bonus and its recruiting place's bonus.

story troops.scout
	title: Scouts
	milestone: 2
	links: map.sight troops.types vintaines.pace map.camera
	description: Scouts are lightly armed troops who see much farther and
		move faster than others, but fight poorly. A vintaine with scouts
		sees more and can move faster at the run, at the cost of fighting
		power; the player chooses the trade.
	value sight: open distance
	criterion 1: unit
		then: A scout's sight radius is {troops.scout.sight}, larger than
			that of every other troop type.
	criterion 2: unit
		then: A scout is faster than every other troop type.
	criterion 3: statistics
		given: Duels between a scout and an equal recruit of any other
			melee type.
		then: The scout loses most of them.
	criterion 4: unit proposed
		then: A scout fights in melee, with a light weapon and no shield.
	criterion 5: unit
		given: A vintaine that gets a scout, whose sight reaches farther
			than the rest.
		then: The camera zooms out until the scout's sight is in the
			window, with the margin.

story troops.tiers
	title: Experience tiers
	milestone: 4
	links: troops.skill economy.salaries
	description: Troops start as recruits and can become warriors (a bit
		better, higher salary) and then veterans (best, highest salary).
		They earn experience by fighting enemies and surviving; troops
		that avoid combat gain nothing.
	value warrior: open count
	value veteran: open count
	criterion 1: unit proposed
		when: A troop kills an enemy troop, player or NPC.
		then: It gains experience by the type and tier of the troop killed.
	criterion 2: unit
		given: A recruit.
		when: Its experience reaches {troops.tiers.warrior}.
		then: It becomes a warrior at once, with the warrior skill; its
			next salary is a warrior's.
	criterion 3: unit
		then: A troop never loses a tier.
	criterion 4: unit
		given: A troop that never fights.
		then: It gains no experience.

story troops.recruit
	title: Recruiting
	milestone: 4
	links: settlements.properties economy.gold centaine.size
	description: Troops are recruited for gold at settlements. Each
		settlement's flags decide which types it offers; the place also
		decides their cost, equipment and skill. Troops never go inside a
		settlement; recruiting only needs a vintaine nearby. New troops join
		that vintaine as recruits.
	value distance: open distance
	criterion 1: scenario
		given: A vintaine within {troops.recruit.distance} of a settlement
			that offers spearmen, and enough gold.
		when: The player recruits 3 spearmen into that vintaine.
		then: The vintaine gains 3 recruit spearmen at its position, and the
			cost is taken from the vasal's gold.

		an epoll loop and a timer for the ticks. Settings come from the
		command line: address, port, map file, data file, web folder,
		allowed origins and, for testing, a seed.
	criterion 1: unit
		when: A setting is missing or wrong.
		then: The server prints what is wrong and exits with a non-zero
			code.
	criterion 2: unit
		when: The server gets SIGINT or SIGTERM.
		then: It closes all connections cleanly and exits with code 0.
	criterion 3: unit proposed
		when: A tick takes longer than its time.
		then: The server logs it and starts the next tick at once; it
			never skips a tick.

story server.web
	title: Serving the client
	milestone: 0
	links: client.platform editor.platform
	description: The server also answers plain HTTP GET requests for the
		client's files (not the editor's). It loads a fixed list of files

		to attack. One process and one port serve everything.
	criterion 1: unit
		when: A request asks for a file that is not on the list.
		then: The server answers 404, whatever the path holds.
	criterion 2: unit
		when: A request uses a method other than GET.
		then: The server answers 405.
	criterion 3: unit
		then: Each file is served with its correct content type.

story build.cmake
	title: CMake
	milestone: 0
	links: build.docker build.scripts
	description: One CMake project with a folder per program and one for
		the engine. Its targets are server, tests, check, client and
		editor. A build tree uses one toolchain, so server, tests and
		check are built in a Linux tree with gcc, and client and editor in
		a web tree with Emscripten. A workflow preset per target picks the
		tree, so building a target is one cmake --workflow --preset
		<target>. The configuration, debug or release, is set by the
		environment variable vasal_config and has a build folder of its
		own (build/linux-<config>, build/web-<config>). Release is the
		default.
	criterion 1: review
		then: Every workflow preset builds from a clean checkout.

story build.docker
	title: Building only in Docker
	milestone: 0
	links: build.scripts
	description: All builds run in one Docker image, which shares the
		project folder, so the output appears in build/. The image holds
		gcc, cppcheck, clang-tidy, Python, CMake and Emscripten (and AFL++
		from milestone 3). The project is compiled with gcc only; other
		tools in the image may be clang-based.
	criterion 1: review
		then: Building needs nothing on the host but Docker.

story build.check
	title: Static analysis and checks
	milestone: 0
	links: security.code build.style tools.check
	description: The check target runs cppcheck with the MISRA C:2012
		add-on and clang-tidy, each program on its own, the specification
		check (tools/spec.py) and the engine's include rule. Accepted MISRA
		deviations are listed in docs/code_style.md and
		.cmake/cppcheck_suppressions.txt.
	criterion 1: review
		then: The check target passes with no findings except the
			documented deviations.

story build.fuzz
	title: Fuzzing
	milestone: 3
	links: security.code build.check
	description: Every parser that reads outside input (HTTP, WebSocket
		frames, game messages, map files, tuning data) has a fuzz target.
		They are built with AFL++ through its gcc plugin, so the project is
		still compiled with gcc only, and run with AddressSanitizer and
		UndefinedBehaviorSanitizer. A fuzz target in the Linux tree runs
		each of them for a set time.
	value time: open ticks
	criterion 1: review
		then: The fuzz target builds every fuzz target with AFL++ and gcc
			and runs each one; a crash or sanitizer finding fails it.

story build.tests
	title: Running tests
	milestone: 0
	links: testing.unit testing.scenarios tools.check
	description: The tests target builds the unit tests and runs them
		through CTest: the C tests (cairo) and the Python tests of the
		tools.
	criterion 1: review
		then: One command builds and runs every unit test.

story build.ci
	title: Continuous integration
	milestone: 0
	links: build.check build.tests
	description: GitHub Actions runs the check, the tests and the release
		builds on every push to main and on demand, in the same Docker
		image, and keeps the release server, client and editor as the
		run's artifact.
	criterion 1: review
		then: A push to main runs the workflow.

story build.scripts
	title: Scripts
	milestone: 0
	links: build.docker build.cmake
	description: The scripts folder holds .ps1 and .sh versions of every
		script, run from the scripts folder. They only wrap commands:
		build_image builds the Docker image, build <target> [debug|release]
		runs the target's workflow preset in it, run_server
		[debug|release] runs the server, passing every other argument on,

		default browser. All default to release.
	criterion 1: review
		then: Every script exists in both versions and behaves the same.

story build.style

		then: The specification check reports files that break the file
